# Архитектурный подход на основе возможностей (capabilities)

* [CleanerFunctionalStaticImpl](https://github.com/extrafix/Clear_Architecture/blob/capabilities/src/main/java/com/summer/cleaner/robot/CleanerFunctionalStaticImpl.java) - содержит реализации функций, которые дергаются в объектах команд.
  Добавлена обработка прокидывания в пользовательский вывод информации о доступности операций.
* [Field](https://github.com/extrafix/Clear_Architecture/blob/capabilities/src/main/java/com/summer/cleaner/field/Field.java) - добавлена проверка без выбрасывания исключения, что бы оповещать пользователя о невозможности операции, но не блокировать ввод последующих.
* [CommandInterpreterTest.testOutBorder](https://github.com/extrafix/Clear_Architecture/blob/capabilities/src/test/java/com/summer/cleaner/interpreter/CommandInterpreterTest.java#L60) - тест на выход за границы поля и установку недоступного режима отчистки.

### Плюсы
* Ввод следующей команды для программиста робота проще, т.к. выбирать он может из доступного

### Минусы
* Больше приходится думать разработчику интерпретатора, чем программисту робота, но это не всегда плюс, т.к. автор интерпретатора что-то может упустить из доступных возможностей робота и его программисту придется использовать костыли, из-за слишком строгих правил интерпретатора, там где они фактически должны быть мягче.

### Мышление письмом
Когда проектировал по Бертрану Мейеру предусмотрел, что возможны ошибки в вводимых пользователем
командах, например, отрицательное значение метров.  
Выбрасывал их выше еще на этапе парсинга команд при переводе их во внутреннию структуру в которой
аргументы имеют верные значения.
Можно сказать этап компиляции программы для робота.
Если введена последовательность команд, которая будет двигать робота за пределы поля, то
Будет ошибка?
Или
просто не будет меняться координата?

	В новом случае архитектуры, надо предусмотреть, что бы робот не просто оставался у края, а еще и была между выполнениями команд специальная функция, которая будет возвращать предварительно выполнение следующей команды с учетом ограничений и либо помечать ее выполнимой полностью, частично или вообще запрещенной
	То есть в список List<Command> в каждую Command надо добавить Capability capability
	capability - enum на 3 значения

Можно сделать ввод команд интерактивным
То есть как в моей игре, сначала вводится команда с System.in, а затем отображать в выводе список
доступных следующих команд

А как можно сделать аналогичное в текущей реализации?
Очень просто, считаю что каждая команда считывает ввод вживую и если команду из списка выполнить не
могу, то пишу об этом соответствущие сообщение, но ошибку прерывающую программу НЕ выкидываю, и беру
следующую команду.

Таким образом будет поведение как и при интерактивном вводе, главное посмотреть как сейчас в таких
частичных ситуациях у меня переключается состояние робота.

Мне нужно, что бы вместо normalizeCoordinates была проверка, которая бы говорила, что следующую
команду выполнить нельзя
Вероятно можно переиспользовать метод isInBorder, поставив его вместо normalizeCoordinates.
Ведь новое состояние присваивается только после успешного выполнения команды.

Я сообщаю, если команду выполнить нельзя, обрабатывая возвращение функцией передвижения null, но что
бы написать в ответе насколько сдвинуться все таки можно, мне надо проектировать более сложную
структуру данных, т.к. информация о размере нехватки.

В моем случае сделал проверку возможности движения вперед и установки режима уборки.
Вокруг оси может поворачивать всегда, если нет выпирающих частей.
Т.к. робот отвечает за состояние, список доступных команд можно внутри него и хранить, если после
каждой команды не просто давать вердикт о ее выполнимости, но пересчитывать список возможных других
команд.
Например, после move на 10, выводить так же список команд (SET [SOAP, WATER], TURN, STOP,
MOVE [50]).
