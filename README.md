## AST

Реализацию от списка комманд вижу в изменении(обертке) комманд в узлы CommandNode и добавление узла типа программа ProgramNode.

В ProgramNode так же добавлен атрибут initialState.   
Можем задавать программу через создание ProgramNode, в который передается список CommandNode и initialState.

Все команды у меня "одноуровневые", то есть нет комманд вроде операторов или циклов, которые бы могли усложнить структуру узлов.

=RequestEvent
Далее идет перечисление типов событий запросов
У них переопределен метод toString, что бы выводит название события реквеста и его аргумент (при наличии)

=DoneEvent
Содержат все типы событий по совершению действия, причем содержат информацию о дельте измененний. То есть старое и новое состояние.
У меня сделано проще, через задание correlationId о том, на какое входящее событие - это исходящее.
Это более однозначно для востановления цепочки, т.к. одно и то же состояние могло быть фактически полученно от двух разных комманд с проблемами в конкурентном доступе, либо между командами могли выполниться другие, которые вернули состояние к какому-то комплексированному до них.   
Эти преобразования сама по себе дельта не покажет, зато эту дельту мы можем показать, если имеет информацию о correlationId, просто написав соответсвующий запрос на сравнение состояний до и после событий.

=StateProjector
Инкапсулирует в себе логику проверки входящего события по типу и формирования DTO с дельтой
Иницилизируется начальным состоянием и выстраивает новое по списку из EventStore

### EventProcessor 
Оперирует и EventStore из которого запрашивает список событий делая его копию (деталь реализации которую я опустил, но подразумевал) и StateProjector, которому передает уже этот список для высчитывания состояние.
Это верно что бы в StateProjector не добавились в список по ссылке новые события во время высчитывания состояния.

Странно что события фильтруются только по тем, что содержат аргументы, а START/STOP не фигурирует, хотя важные логи они тоже создают.

?где проигрывается START/STOP?
Обработку этих событий засунули в StateProcessor, что начинает создавать путаницу, т.к. state уже многозначный термин в программе, намного шире чем выбор режима мойки.

Процессор так же частично реализован как абстрактный класс в который вынесена часть логики
Процессор же в потомках после выполнения команды и генерации исходящего события, добавляет его в EventStore

Так же есть LoggingProcessor, который фактически будет вызываться вторым на каждый тип события, т.к. 1 раз вызовется из списка processors нужный для события класс, который НЕ создаст ошибку, а во второй LoggingProcessor, который обрабатывает события всех типов так же без ошибки.
Мой вариант с мапой по типу события - определенней.
